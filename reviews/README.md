# アプリ版の点検（毎回の変更と、毎日の定期）

2026-10-21 satouさん「カンバンにも、LAST TELL と同じようなチェック機構を入れてほしい」「定期的なチェックもするように」。
ボード側と同じ形（役・観点・重さ）。正はデータ側のリポジトリの `board-src/reviews/README.md`、手本は LAST TELL の `qa/UIUXレビューの手順.md` など。

## なぜこの形か（出典）

- 何人かが別々に見ると見落としが減る。1人だと問題の約35%、3〜5人で約75%（Nielsen「How to Conduct a Heuristic Evaluation」NN/g）。→ 2つの役を、別々の Agent（前の会話を知らない目）で見る。
- 指摘には重さを付け、重いものから直す（Nielsen「Severity Ratings for Usability Problems」NN/g：0 問題でない〜4 必ず直す）。
- 使う人の目線は、その人の目的と手順をなぞって確かめる（Cognitive Walkthrough、Wharton ら 1994）。
- UI/UX 専門家は NN/g の10の原則（Nielsen 1994）と WCAG 2.2（文字の明るさの差 1.4.3・押す所の大きさ 2.5.8・名前 4.1.2）。

## 何を見るか

アプリだけの部分：上のバー（💬 ↻ ⋯ 🎨 🎤 ＋）・状態の1行（#lkStatus）・会話の欄（💬 ポチ。talk.js・voice.js・koe.js）・設定（⋯ → 🎤と会話・AI の設定）・隅のポチ・つなぐ前の画面・notes/（メモ）。
ボードそのもの（列・カード・詳細）はボードの写しなので、ボード側の点検が見る。アプリの中で崩れていないか（重なり・はみ出し）だけ見る。

## 1. 変更ごとの点検（PR ごと・必ず）

画面に出るファイル（index.html・app.js・app.css・boot.js・shim.js・talk.js・voice.js・koe.js・localai.js・ear-worker.js・bg/・notes/index.html）を直す PR では、次をすべてそろえる。CI「QA」の `qa/check-review.mjs` がそろっているかを見る（無いと赤）。

1. `sw.js` の `CACHE = 'kanban-v<番号>'` を1つ上げる（端末にも届く。これが版の番号）。
2. 自動の検査を全部回す：`node qa/run.mjs`、`node qa/check-uiux.mjs`（使いやすさの数字）、本物のボードの写しがあれば `LK_BOARD=<写し>` でも。速さは `LK_BOARD=<写し> node qa/speed.mjs`。
3. 画面写真を撮る：`LK_BOARD=<写し> node qa/check-uiux.mjs --shots <フォルダ>`（スマホ・PC・暗い色 × ボード・詳細・会話・設定）。
4. 2つの役を、別々の Agent で見てもらう（同じ写真と、変えた所の説明と、下の表を渡す。役どうしの答えは見せない）。写真を見ずに点検しない：記録に「写真：」で始まる行（どの画面・幅・色を何枚見せたか）を書く。無いと `qa/check-review.mjs` が ❌（ボードの点検と同じ。2026-10-21）。
   - **使う人の目線**（satouさん役）：下の「柱」と7つの観点。
   - **UI/UX 専門家**：NN/g の10の原則と WCAG、自動の数字。
5. 交代の視点を1つ深く見る（版の番号を5で割った余り。下の表）。自分で見てよい。
6. 指摘を直す。重さ 3・4 は公開前に必ず直すか、大きな作り替えなら satouさんにボードのカードで聞く（その行に「直した」か「satouさんに聞いた」と書く。ボードそのものの指摘は、ボードのスレッドへ送って「ボードのスレッドに渡した」と書く）。重さ 1・2 は同じ PR で直すか、この下の「次の候補」へ。
7. 機械で確かめられる形にできた指摘は `qa/check-uiux.mjs`・`qa/run.mjs` に足す（以後は毎回自動）。
8. 結果を `reviews/v<番号>.md` に1枚（ボードと同じひな形）。数字が良くなったら `node qa/check-uiux.mjs --update-baseline` で基準を下げる（悪くなったときに基準を上げてはいけない）。
9. **押す所（ボタン・リンク・欄）は増やさないのが基本**（2026-10-21 satouさん「ボタンが増えたことによって、UI/UXに影響がでていると思います。こちらのチェックも」。前にも言われていた）。`qa/check-uiux.mjs` は画面ごと（ボード・カードの詳細・会話・設定）に押せる部品の数を数え、全部の数が基準より1つでも増えたら ❌（最初の画面の数は、CI と手元で日本語の字の形が違って画面の下の端の1つが出入りするので、+1 まで見逃す）。どうしても足すときは、先に同じ画面で1つ減らすかまとめる（⋯ にしまう・2つを1つに・使う時だけ出す）。それでも増えるなら基準を上げ、`reviews/v<番号>.md` に「## 増やした押す所」（何を足したか・なぜ要るか・代わりに減らした／しまったもの）を書く。無いと `qa/check-review.mjs` が ❌。

## 2. 毎日の定期の点検

毎日、ボードの定期の仕事「カンバンの自動改善（毎日）」（11:23。ボードの点検のあと、ボードの写しが新しくなってから）が、続けて同じ点検を **アプリ全体** に対して行う（定期の仕事を1つにまとめてトークンを節約する）。変更が無い日も行う。

- 本物のボードの写し（データ側 `board-src/kanban.html` か共有フォルダ `board/kanban.html` の新しいほう）で、`qa/run.mjs`・`qa/check-uiux.mjs`・`qa/speed.mjs` を回す。前の日より悪くなった数字があれば、それを今日直すものの第一候補にする。
- 2つの役を、別々の Agent で全体を見てもらう。交代の視点は曜日で回す（月 初めて見る人・火 アクセシビリティ・水 スマホ・木 速さ・金 言葉・土日 会話（ポチ）を通しで）。
- 結果は `reviews/daily-<日付>.md`（形はひな形と同じ。変えた所は「定期」）。重さ 3・4 があれば、その日に 1. の手順で PR を出して直す。無ければ記録だけの PR（自動マージ）。
- ボードのカード `th-local-kanban` の history に1行（「M/D の定期点検：結果1行」）。
